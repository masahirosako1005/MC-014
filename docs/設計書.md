## 2. 大会規定への対応

| 規定 | 対応 |
|---|---|
| PHPの利用禁止 | サーバを Node.js + Express で実装した |
| 外部APIへの接続禁止（国土地理院は可） | CSPヘッダで、ブラウザの通信先を自サーバと `cyberjapandata.gsi.go.jp` に制限した |
| 同上（AI） | クラウドのAIサービスを使わず、行動判断をサーバ内で計算する（7章） |
| 同上（経路） | 経路検索APIを使わず、開発時に国土地理院の道路データから全経路を計算し、ファイルで同梱した（8章） |
| 同上（ライブラリ） | CDNを使わず、Leaflet と jsQR を `public/vendor/` に同梱した。文字はOS標準を使う |
| 同上（他のユーザー） | サーバ間の通信はできないので、他の人の推しはサーバ内で動かすデモデータとした（9章） |
| 同上（京町ありさ） | スタンプラリーの画像は実行時に取得せず、切り抜いてアプリ内に同梱した |
| 同上（ルート作成） | 生成AIを使わず、サーバ内の点数計算と用意した天の声の文章で作る（16章） |
| 同上（天気） | 天気予報のAPIには接続しない。天気は lib/calendar.js で創作する。本物の天気に切り替えるコード（Open-Meteo の例）は lib/calendar.js の【API差し替え箇所】にコメントアウトして残し、以前使っていた開発時の取得スクリプト tools/fetch-weather.js もコメントアウトした |
| 同上（イベント） | 開発時に公開情報を確認してサーバ内に持ち、管理画面で更新する（15章） |
| 同上（既存アプリ） | `app.raund.net` とは通信しない。設定画面に、画面遷移のためのリンクのみ置く |

CSPが効くのはブラウザからの通信のみである。サーバ側のコードは実行時に外部へ通信しない。`tools/` のツールは開発時にのみ国土地理院へ接続する。

## 3. デザイン

ゲームの画面のようなデザインとする。実際の地図を舞台にし、情報はパネルとして重ねる。操作はアイコンのボタンで示して文字を減らし、ボタンは押し込める厚みを持たせる。文字は丸ゴシック、文字と線は濃い藍色とする。

| 指定色 | 役割 |
|---|---|
| `#007190` | 主要な色。ボタン、リンク、足あとの線、地図の足取りと区切り |
| `#b5decc` | 面の色。作品の世界の色、キャラの背景、出会いの行の背景 |
| `#ffdd00` | 強調。作品の世界の色、選択中のタブと切り替え、エリアのボタン、ホームにいる印、ロゴの「！」、今日の印 |

このほか、本文の黒に近い文字色と、灰色の補助文字、細い線を使う。キャラの絵はキャラごとの色を持つ。

### 革新的な要素

- **地図の舞台:** 推しが実際の道を移動し、位置が変わると滑らかに動く。エリアへ連れて行くと地図の上に現れて動き出す。
- **足あとの線:** 読み進めた分だけ点線に色が付き、推しの顔が線をたどる。

### スマホとPC

900px を境に画面を組み替える。スマホの画面を拡大するのではなく、広さを活かす。

| 画面 | スマホ | PC |
|---|---|---|
| タブ | 下部 | 左の列（順番は同じ） |
| ホーム | 地図に推しのカードを重ね、足あとを下から引き上げる | 地図の右に、推しのカードと足あとの列を常に出す |
| ミニ推し | 2列 | 作品のカードを横に並べ、推しも列を増やす |
| エリア | 一覧とカレンダーを切り替える | 一覧とカレンダーを並べる |
| 推しのページ | 縦に並べる | 左に絵と操作、右に図鑑 |
| ルートの結果 | 文章の途中に地図 | 左に文章、右に地図を固定 |
| 詳細 | 下からのシート | 中央の窓 |

`prefers-reduced-motion` を設定している端末では、アニメーションを止める。

## 4. 画面

ロゴ「ミニ推し！」を全タブの最上部に置く。下部タブは ①ホーム、②出会う、③ミニ推し、④観光ルート、⑤エリア、⑥設定 の6つ。

| 画面 | 内容 |
|---|---|
| ①ホーム | 地図の舞台に、ホームに選んだ推しのカード（横スライドで切り替え）、エリア、ルート、イベント、現在地のボタン、足あと（タイムライン、歩数と距離）を重ねる。エリアへ連れて行っていない推しは待機の画面になる。30秒ごとに最新の状態へ更新する。地図は拡大と縮小のボタン、ピンチ、PCのホイールで拡大縮小できる |
| ②出会う | QRコードの読み取りとコード入力を切り替えて、キャラやエリアを獲得する |
| ③ミニ推し | 「わたしの推し」と「旅先で出会った推し」を切り替える。前者は分類と作品ごとに並べ、あらすじと権利表記を添え、推しごとにホームへ出すかを選ぶ。後者は出会いの記録を時系列に並べ、閲覧のみとする |
| ④観光ルート | 保存した観光ルートの一覧。推しごとに絞り込め、詳細を開ける。新しいルートもここから頼める |
| ⑤エリア | 獲得したエリアの一覧とイベントカレンダーを切り替える。一覧に地図は出さない。押すとエリアの情報、主な場所、過去の旅の履歴が見られる |
| 推しのページ | プロフィール、性格、行動原理、いつもの道、よく通う場所、足あとの集計、作中の出来事、作品の権利表記 |
| ルート作成 | 組み合わせ、エリア、期間、長さを選ぶ。「推し×自分」のときだけ気分も伝えられる。結果は天の声の文章で読み、地図で見て、一緒に歩くモードで進める |
| プロフィール | 呼び名（任意）、好きなもの、歩ける量。一番下に控えめなログインボタンを置き、押すと下からログインと登録の入力欄が開く |
| ⑥設定 | プロフィールの入口、解釈違いの報告、地図の種類（既定は写真）、タイムラインの順番、文字の大きさ、デモ操作、アプリの説明 |
| 場所の詳細 | 場所名を押すと下から開く。地図、説明、種類、住所、今日立ち寄ったキャラ、公式サイトなどへのリンク |
| 他の人の推しの詳細 | 閲覧のみ。相手が獲得した場所、地域の紹介、地域の公式サイトへのリンク。こちらの推しの紹介が相手にも届いていることも示す |

獲得数の母数（全部で何種類あるか）は、どの画面にも出さない。

### タイムラインの書き方

最初は今日の分を文章で表示し、カレンダーで選ぶと過去の日も見られる。キャラに喋らせず、第三者の視点で書く。訪れた理由は表示しない。

```
14時17分、ルイが喫茶キツネ雨を訪れた。
店の前で猫の姿を探してから、ようやく中へ入った。

12時20分、ルイが千光寺山ロープウェイで山頂駅へ上がった。

15時24分、ありさが尾道浪漫珈琲本店で、上田から旅してきた信繁に出会った。
```

歩数と距離は「今日 7,710歩 ・ 5.2km」とだけ表示する。

### 地図

地図はタイムラインより小さく置き、「地図を広げる」で大きくできる。歩いた道を点線、乗り物を実線で描く。獲得したエリアの外側を暗くし、境目に線を引く。

広げたときは「市全体」のボタンで、獲得したエリア全体を表示できる。

### 獲得の方法

京町ありさは初期キャラで、最初から一緒にいる。他のキャラとエリアは、スポットのQRコードと掲示物のコードで獲得する想定で、現地へ行かないと手に入らない。

| 方法 | 動作 |
|---|---|
| カメラ | 映像を jsQR で解析する。HTTPSまたはlocalhostでのみ使える |
| 写真から読み取り | カメラが使えない環境向け。撮影した写真を jsQR で解析する |
| コード入力 | 大文字小文字と前後の空白を無視して照合する |

## 5. システム構成

```
スマートフォン / PC のブラウザ
  │  画面: HTML / CSS / JS（フレームワークなし）
  │  地図: Leaflet + 国土地理院タイル   QR: jsQR
  │
  │  HTTP（JSON）
  ▼
Node.js + Express（server.js）
  ├─ lib/simulator.js   行動判断AIと旅の計算
  ├─ lib/planner.js     カップリングルートの作成
  ├─ lib/calendar.js    天気と祝日
  ├─ lib/auth.js        パスワードとログイン
  ├─ lib/content.js     運営が管理する内容（data/content.json）
  ├─ lib/store.js       ユーザーごとの進行状況の保存（data/state.json）
  ├─ data/world.js      作品、エリア、場所、交通、キャラ、獲得コードの初期値
  ├─ data/canon.js      キャラの公式設定、日常、天の声の文章の初期値
  ├─ data/events.js     イベントと祝日の初期値
  ├─ data/travelers.js  他の人の推し（デモ用）
  └─ data/routes.json   全場所間の経路（開発時に生成）

運営者のブラウザ（このPCのみ）
  ▼
管理画面サーバ（admin/server.js、ポート3100）  同じ lib/content.js を読み書きする
```

`state.json` と `content.json` はJSONファイルである。localhostで動かす前提のためDBは使わない。

## 7. 行動判断AI

外部APIが使えないため、LLMではなくユーティリティAIで実装した（`lib/simulator.js`）。滞在を終えるたびに、次の手順で行き先を決める。

1. **候補を絞る:** 行けるエリアの場所のうち、到着時に営業している目安の時間内のものを残す。現在地、自宅、宿、学校、休止中の場所は除く。平日の帰り道は `routine.pool` に絞る（14章）
2. **点数を付ける:** 候補ごとに次の式で計算する
3. **選ぶ:** 最も点の高い場所へ向かう
4. **過ごし方を選ぶ:** 場所専用、キャラ固有、カテゴリ共通の順に、描写の文章を選ぶ

```
点数 = 関心の強さ × 3
     + 時間帯の適合（昼食どきの食事、夕方の景色など）
     + 未訪問なら 好奇心 × 1.5
     + その日初めて乗る乗り物なら 乗り物好き × 1.8
     + よく通う場所なら 重み × 2
     + 関心の高いイベントの開催中なら 関心 × 5
     − 今日の訪問回数 × 2.5
     − 雨の日の屋外なら 3
     − 直前と同じ種類の場所なら 1
     − 食後4時間以内の食事なら 4（食べることが最優先のキャラは1.5）
     − 歩く距離 ÷ 距離の許容 − 乗り物の待ちと乗車の分数 × 0.05
     + ゆらぎ（0〜0.8）
```

歩数は `歩いた距離 ÷ 歩幅` で求める。乗り物の区間は含めない。

### 記録を保存しない理由

旅の記録は保存せず、獲得日の前日からその都度計算する。乱数の種を「キャラと日付」で固定しているので、何度計算しても過去は変わらない。これにより、保存データは獲得状況と設定のみで済む。

## 8. 経路の生成

`tools/build-routes.js` が開発時に一度だけ実行し、`data/routes.json` を作る。アプリはこのファイルを読むだけで、実行時に外部へ接続しない。

| 手順 | 内容 |
|---|---|
| 1. データ取得 | 国土地理院のベクトルタイルから、道路中心線（`experimental_rdcl`）と鉄道中心線（`experimental_railcl`）を取得する |
| 2. グラフ作成 | 道路をノードと辺のグラフにする。タイルの境界で切れた線はつなぐ。高速道路は除く |
| 3. 乗り物の追加 | 乗り場を道路につなぎ、乗り物の辺を足す。電車は線路、バスは道路に沿い、渡船は直線、ロープウェイは索道データの端点を直線で結ぶ |
| 4. 坂の考慮 | 道路データに高さがないので、千光寺山の斜面の範囲は歩く時間を6倍に見積もる。山頂側との行き来でロープウェイが選ばれやすくなる |
| 5. 経路探索 | 所要時間が最短の経路をダイクストラ法で全組み合わせ（1,128通り）求める |
| 6. 保存 | 徒歩と乗車の区間に分け、線を間引いて保存する（約890KB） |

移動中のキャラの現在地は、時刻に応じて経路の線上を進む。

## 9. 他の人の推しとの出会い

別のユーザーが遠くの町で獲得した推しを尾道に旅させている、という想定で、3人の推しをサーバ内で動かしている（`data/travelers.js`）。足取りは自分のキャラと同じ行動判断AIで計算する。

- **出会いの条件:** 同じ場所に同じ時間にいたとき。同じ相手とは1日1回まで
- **見られるもの:** 相手が獲得した場所、その地域の紹介、地域の公式サイトへのリンク
- **閲覧のみ:** 出会った推しを自分の推しとして旅に出すことはできない
- **互いに見られる:** こちらの推しの獲得した場所が相手に届くことを画面で示す。実際に相手へ送る処理は、ユーザー間で共有するサーバを用意する本番で実装する

| GET | `/api/report-kinds` | 解釈違いの種類の一覧 |
| POST | `/api/reports` | 解釈違いの報告。獲得済みの推し、決まった種類、5〜1000文字の内容だけを受け付け、1人1日20件まで。state.reports に保存し（最新1000件）、外部へは送らない |

## 14. 推しの世界と日常（2026年11月の追加）

### ホーム: 一人の推しの世界

キャラのアイコンを並べて選ぶ形をやめた。ホームに出すのは、ミニ推しの一覧で家のアイコンを押した推しだけで（`homeCharacterIds`）、獲得しただけでは並ばない。上部の推しのカードを横にスライドして切り替える。次の推しが端に見えるので動かせることが分かり、PCでは左右の矢印も出す。作品の色は指定の3色から作った3種類（`data-theme`）のみ。

主役は旅を見ることなので、足あとのパネルと地図を常に見せる。

**デイ・リプレイ（1日をなぞるつまみ）** 足あとの見出しのすぐ下に、6時から24時までの濃紺の帯を置く（public/js/scrubber.js）。帯の中に時間ごとの歩数を黄色の棒で、帯の上に時間ごとの天気を、帯の縁に出来事の印（訪問は白、乗り物は水色、出会いはミント、神の手は黄色）を並べ、推しの顔のつまみを左右になぞる。時間、天気、歩数、出来事、地図をばらばらの部品で見せていたのを、1本の時間の軸と1つの動作にまとめるのがねらい。

| 状態 | つまみ | 地図 | 下の文 |
|---|---|---|---|
| ライブ（今日、触っていない） | 今の時刻。黄色の波と「いま」 | 今の推しと今日の足取り（いつもの表示） | なぞると見返せるという案内。右に「ライブ」 |
| リプレイ（なぞった） | 指を離した時刻のまま止まる | その時刻までの道を濃く、その後の道とまだ着いていない場所のピンを薄く描き、推しをその時刻の位置に置いて追いかける | その時刻の推しの様子（「靱公園にいる」「大阪メトロ千日前線で阿波座駅へ向かっている」など）。右に「いまに戻る」 |
| 過去の日 | 何もしなければ右端で薄く（1日全体） | 1日分の足取り。なぞるとリプレイと同じ | 右に「1日全体を見る」 |

- 推しの位置は、足取りの区間の時刻（サーバが todayLegs と legs に付ける startAt、endAt）から map.js の positionAt で求める。区間の途中なら線の上の進んだ位置、区間の間なら直前の区間の終わり。
- ピンには着いた時刻（at）を付け、なぞっている時刻より後のピンを薄くする。今日の時間ごとの歩数は hourlySteps で返す。
- 出来事の印の9分以内では、つまみが印の時刻に吸い付く。今日は今より先へなぞれず、今の時刻まで戻すとライブに戻る（今より後の部分は斜線で、これからの天気だけが見える）。
- その時刻の直前の出来事を、タイムラインで選んだ状態にする。逆にタイムラインの行を押すと、つまみがその時刻へ動き、地図はその場所を真ん中にする。
- なぞっている間も30秒ごとの更新は続け、地図はなぞった時刻のまま描き直す。
- キーボードでは帯にフォーカスして左右の矢印で10分ずつ、Home と End で端へ、Esc でライブに戻る。読み上げ用に role="slider" と時刻の aria-valuetext を付ける。
- 過去の日の記録パネルからは、時間ごとの天気と歩数の棒を省く（つまみで見せる）。

足あとの見出しの日付から過去の日を選ぶと、文章と地図の道のりがその日のものになる（`GET /api/characters/:id/journey/:day`）。足あとのある日は `activeDays` で返す。過去の日には、リングと時間ごとの歩数の棒（public/js/dayview.js）と、天の声の日記（lib/diary.js）を足あとの上に出す。日記は実際の訪問の記録だけから作り、同じ日は同じ文章になる。リング1周はその推しのいつもの日（今日を除く足あとの平均）とし、順位や達成の言葉は使わない。旅は毎回最初から計算しているので、過去の日も同じ内容を再現できる。地図には、乗り物（data/world.js の TRANSIT）の乗り場から作った駅、バス停、桟橋、ロープウェイの駅を出す。server.js の transitStops が、同じ乗り場を1つにまとめて路線名を並べ、近く（250m以内）に駅の場所があれば placeId を付け、獲得したエリアの中のものだけを /api/state の stops で返す。public/js/map.js の drawStops が、足取りより下の層に小さな白い印で置く（拡大率13未満では隠す）。タイムラインの訪問の行は、その場所まで歩いた距離（walkM）を、乗り物の行は乗り物で移動した距離（meters。経路の座標をたどって測る rideMeters）を持ち、行の終わりに小さな札で見せる。タイムラインの各行は、その出来事の場所の緯度経度を data-lat と data-lng に持つ。行を押す（Enterキーも可）と focusLine が、地図の見えている部分（スマホでは足あとのパネルの上）の真ん中にその場所が来るよう、ズーム16以上で flyTo し、場所に黄色の輪を2.4秒出す。「観光ルートを考えてもらう」と「このエリアのイベント」は舞台の脇のボタンから開く。イベントのボタンは、推しが今いるエリアのイベントだけをシートで見せる。

### 使い方の説明と保存したルート

使い方は `public/js/guide.js` の6枚のカードで、初回だけ自動で出す（`guideSeen`）。設定から見直せる。観光ルートは作成時に自動で保存し、大メニューの「観光ルート」（`#/routes`、`public/js/views/routes.js`）で一覧、`#/route/:id` で詳細を見られる。

### 時間の感覚（夜遅くに移されたとき）

キャラごとの `night`（`data/canon.js`）に、時間の感覚を持つ。神の手が lateHour 時より後にエリアを移すと、知らない土地を楽しむ描写ではなく、帰るか泊まるかを考える描写になり、その日の寄り道をやめる（lib/simulator.js の nightPlanOf と settleNight）。

| 条件（上から順に判断） | 行動 | 描写 |
|---|---|---|
| 家まで30分以内 | まっすぐ家へ帰る | near（なければ goHome） |
| 次の日が学校や仕事の日（mustReturn） | 遠くても、その夜のうちに家へ帰る（新幹線でも帰る） | workday |
| 次の日が休みで、家まで stayIfFarMin 分以内 | 家へ帰る | goHome（高校生は家に電話をしてから） |
| 次の日が休みで家が遠く、45分以内に宿がある | いちばん近い宿に泊まり、次の朝からそのエリアで動く。タイムラインには「〇〇に泊まった」 | stay（高校生は家に電話をして許しをもらってから） |
| 宿がなく、camp のキャラ（武蔵） | 移された駅で朝まで夜を明かす | camp |
| それ以外 | 家へ帰る | goHome |

| キャラ | lateHour | 次の日が休みのとき泊まる目安 | 特徴 |
|---|---|---|---|
| 京町ありさ（高校2年） | 19時 | 帰るのに90分より長い | 学校の前の日は焦って帰る。休みの前の日は家に電話をしてから決める |
| 堀江 凪（高校2年） | 19時 | 90分 | 祖母を気にかける |
| 月島こはる | 21時 | 60分 | 締め切りの前の日は帰る |
| 西ノ丸あかね | 18時 | 60分 | 朝型。泊まって翌朝から調べる |
| 風早ルイ | 22時 | 60分 | 夜に強い |
| 小早川隆景 | 19時 | 60分 | 夜の移動を避けて宿に入る |
| 宮本武蔵 | 21時 | 30分 | 宿がなければ駅で夜を明かす |

次の日が学校や仕事かどうかは、routine.anchor の曜日と祝日で決める。起きる前（夜中から朝）に移されたときは、起きる時刻から動き出す。

### 知らない土地での振る舞い

キャラごとの `away`（`data/canon.js`）に、地元以外のエリアでの性格を持つ。`arrivalStayMin`（駅で動き出すまで）、`rangeFactor`（歩く範囲）、`stayFactor`（滞在の長さ）、`curiosityFactor`（初めての場所への関心）、`boost`（場所の種類ごとの関心の増減）、`maxStops`（立ち寄りの上限。超えると帰る）で行動を変え、`arrive`、`again`、`back`、`firstVisit`、`doing` の文章で描写する。

### 宮本武蔵と創作の履歴

武蔵は道場とジムだけに強い関心を持つ。架空の8施設（`data/world.js` の `DOJO_PLACES`）は `onlyFor` で武蔵だけの候補とし、`noRoute` でルート作成から外す。創作の履歴（`data/demo-history.js`）は「何日前の何時に、神の手がどのエリアへ連れて行ったか（移したか）」だけを持ち、足あとは通常の計算で作る。時刻を省いた行は朝5時（起きる前）、エリアが null の行は「家に帰した」。一か月の間に、昼間の移動、夜遅くの移動、家に帰す日をときどき入れてある。夜遅くの移動は時間の感覚で、学校の日の朝早くの移動は night.lines.morning（学校に間に合う電車を探す）で描写する。何曜日にあたるかは開いた日で変わるので、学校の前の夜なら帰り、休みの前の夜なら泊まる、のように結果も変わる。入れた記録には demo の印を付け、DEMO_HISTORY_VERSION が変わると起動時に創作の分だけを入れ替える（利用者が自分で連れて行った履歴は残す）。

### エリアへ連れて行く

推しは常に旅をしているわけではなく、エリアへ連れて行った時刻から行動を始める。旅に出ていない推しは家で待っていて、ホームは待機の画面になる。エリアは1つだけ選ぶ。ホームと推しのページのボタンから選び、押すとすぐ出発する（`PUT /api/characters/:id/travel`）。`areaId` を null にすると、その場で家に帰して旅を終え、タイムラインに「神の手が〇〇を家に帰した」と出す。

連れて行った履歴は時刻つきで保存する（`travelLog`）。計算時に `calendar.placementAt(ms)` でその時刻のエリアを引き、置かれていない日は動かない。旅は毎回最初から計算し直すが、変更前の時刻には変更前のエリアが使われるので、過去の足あとは変わらない。

エリアを切り替えると、その時刻に今の行動を切り上げて移動先の最初の駅へ移り、タイムラインと日記に「神の手が〇〇を□□エリアに移動させた」と出す。切り替えの間は「エリア切り替え中」のポップアップを出す（`calendar.moves`）。翌日以降の学校や仕事の日課は変えない。同じエリアのまま初めて連れて行くときは、授業の時間なら寄り道せず学校へ向かい、日課の終わった後なら日課を飛ばす。放課後と休みの日は連れて行ったエリアを旅し、別の地方へ連れて行ったときは帰りの時間を見込んでその日のうちに家へ帰る。

### 公式設定（data/canon.js）

キャラごとに、プロフィール、性格、好きなもの、通学や通勤の経路、よく通う場所、作中の出来事、関係、日常の決まり、イベントへの関心と反応、ルート作成の天の声の文章（`narration`）を持つ。推しのページ（`#/oshi/:id`）に表示し、同じ値を行動判断とルート作成に使う。京町ありさの作中の地名はスタンプラリーのサイトから取り、モデルの場所を大阪市西区の実在の場所に対応させた。

### 日常の行動（lib/simulator.js）

| 条件 | 行動 |
|---|---|
| 平日（祝日を除く） | `routine.anchor` の時刻から逆算して家を出て、通り道（`via`）を通って学校や仕事場へ向かう |
| 帰り道 | `routine.pool` の場所に `afterStops` か所まで寄る。雨の日は `rainStops` か所で、0ならまっすぐ帰る |
| 休みの日 | 従来どおり自由に動く。雨の日は屋外の場所を減点し、出かける数を減らす |
| 遠出 | 休みの日に `tripChance` の確率で、獲得済みの別の地方へ行く。関心の高いイベントがあれば確率が上がる |

天気は `lib/calendar.js` が創作で決める（外部のAPIには接続しない）。

| 関数 | 内容 |
|---|---|
| pseudoWeather(日付, 地方) | 1日の天気。地方と日付から決まる乱数と、月ごとの雨の確率の目安で、晴れ、くもり、雨を決める。尾道市と三原市は同じ瀬戸内なので同じ天気になる |
| hourlyWeather(1日の天気, 日付, 地方) | 0〜23時の天気。晴れの日は昼過ぎに雲が出ることがあり、くもりの日は晴れ間がのぞき、雨の日は5〜15時に降り始めて4〜9時間降る（半分の日はもう一度短く降る） |

優先順は、管理画面の上書き、創作の天気。上書きした日は、時間ごとの天気も上書きした天気から作り直す。推しは、いるエリアの天気で行動し、立ち寄る場所を選ぶときは、その時間に雨が降っていれば屋外の場所を避ける。足あとのAPIは、今日と過去の日の時間ごとの天気（hourlyWeather）を返す。時間ごとに、推しがその時間にいたエリアの天気を使う。画面では、ホームの1日をなぞるつまみ（public/js/scrubber.js）が6〜23時を時間ごとの歩数と同じ幅で並べ、夜の晴れは月で見せる。

実環境で本物の天気に切り替えるときは、lib/calendar.js の末尾の【API差し替え箇所】のコメントアウトを外す。サーバが起動時と1時間ごとに時間ごとの天気をAPIから取って覚えておき、weatherOf と hourlyOf はその結果を先に返す（推しの行動の計算から何度も呼ばれるので、APIを直接呼ばない）。

### イベントへの反応

イベントの種類（`tags`）とキャラの `eventTags` から関心（0〜1）を求める。

| 関心 | 行動 |
|---|---|
| 0.7以上 | 開催中で時間帯が合えば、会場の点数が大きく上がり、足を運ぶ |
| 0.35以上 | 駅でポスターに足を止める |
| 0.35未満 | 駅でポスターの前を通り過ぎる |

ポスターは開催の21日前から、その地域の駅に貼られている扱いにする。描写は第三者視点で、キャラに喋らせない。

## 15. カレンダーとイベント

`data/events.js` が初期データで、管理画面で追加と編集ができる。⑤エリアのタブに月のカレンダーを置き、獲得したエリアのイベントだけを見せる。何か月も続くイベントで全ての日に印が付くと意味がなくなるので、90日を超えるものは一覧にだけ出す。日程が公式に確認できていないものは `tentative` を付け、画面に「予定」と出す。

## 16. カップリングルート作成（lib/planner.js）

推しが自分のために観光ルートを考える機能。「推し×自分」と「推し×推し」を選べる。候補地ごとに次の点を合計し、時刻を進めながら最も点の高い場所を順に選ぶ（貪欲法）。

入力画面の上にある推しの画像を押すと、推しを選ぶシートが開き、考えてもらう推しを変えられる。選んだ日付はURLの from と to で引き継ぎ、エリアは新しい推しのいるエリアに選び直す。推しが一人だけのときは、画像は押せない。

| 材料 | 内容 |
|---|---|
| 公式設定 | 推しの関心、よく通う場所 |
| 足あとの蓄積 | タイムラインの計算結果から、場所ごとの訪問回数と滞在時間を集計したもの（`summarizeVisits`） |
| 自分 | プロフィールの好きなもの、歩ける量 |
| もう一人の推し | 関心、よく通う場所、足あとの蓄積。歩く距離と速さは遅い方に合わせる |
| 気分（「推し×自分」のときだけ） | 選択肢と、言葉の入力を辞書で読み取った結果。目的は聞かない。推しが考えたルートであることに価値があり、個性も出しやすいため |
| イベント | 期間の中で関心の高いイベントのある日を選ぶ。夜のイベントは最後の目的地にして一日を組み立てる |
| 時刻 | 営業時間内に到着する。食事の時間帯は食事の店を選びやすくする |

学校、自宅、宿、休止中の場所は候補に入れない。文章は一番大きい理由に合うものを `narration` から選び、同じ文章を繰り返さない。選んだ理由は画面に根拠として出す。

ローディング画面の文言は、実際に計算に使った材料から作る（`thoughts`）。「一緒に出かける」は、地図を見ながら1か所ずつ天の声の文章を読み進める全画面の表示で、位置情報は使わない。

**移動手段** 観光ルートでは、歩くだけでなく、公共交通機関とタクシーも使う（推しの日常の行動はこれまでどおり）。lib/planner.js の chooseLegs が区間ごとに決める。

| 条件 | 行き方 |
|---|---|
| 歩く距離が上限（推しと利用者の歩ける量から決まる。最低700m）以内 | 経路（routeBetween）のまま。電車、地下鉄、バス、渡船、ロープウェイが入っていればそれも使う |
| 公共交通機関が入る区間で、歩く距離が上限の1.6倍以内 | 公共交通機関を優先して、そのまま使う |
| それより歩く区間 | 区間をまるごとタクシーにする（タクシーと電車を乗り継ぐ不自然な行き方にしない）。渡船やロープウェイの区間は、それを残して長い徒歩だけをタクシーにする |

入力画面の「移動手段」で、公共交通機関とタクシーをそれぞれ使うか使わないかを選べる（どちらも最初は使う）。選んだ手段は POST /api/routes の useTransit と useTaxi で送り、ルートにも保存して「条件を変えて考えてもらう」に引き継ぐ。

| 選択 | 行き方 |
|---|---|
| 公共交通機関とタクシー | 上の表のとおり |
| 公共交通機関だけ | タクシーに置き換えない |
| タクシーだけ | 乗り物の入る区間はまるごとタクシー。ロープウェイの区間は山道を歩いて登り、長い徒歩だけタクシー |
| どちらも使わない | 歩くだけ。地下鉄やバスの区間は道に沿って歩き、ロープウェイの区間は山道を歩いて登る |

公共交通機関を使わないときは、渡船でしか渡れない向島の場所へは行けないので、候補から外す。

タクシーは道を歩く道と同じ線で描き、時速約21km（350m/分）と乗り場で待つ5分で時間を見積もる。使うと少し減点するので、近い場所は歩きで選ばれやすいまま、遠い場所もあきらめずに済む。各場所には前の場所からの行き方（access）と出発時刻（departAt）を付け、区間には何か所目へ向かうか（stop）を付ける。合計には乗り物とタクシーの距離（rideM）を足した。

**行き方の内訳（access）** 1つずつに、手段（walk、taxi、train、bus、ferry、ropeway）、名前、距離、かかる時間（待ち時間を含む minutes と、そのうちの waitMin）、始まりと終わりの時刻（startAt、endAt）を持つ。公共交通機関は、乗る駅（from）と降りる駅（to）を持つ（経路を逆向きに使うときは入れ替える）。続けて歩く部分は1つにまとめる。時刻は到着時刻と同じ式で積み上げるので、最後の終わりの時刻は場所の到着時刻と一致する。

**地点と移動の並び**（public/js/route-flow.js の routeFlow） 観光ルートを「地点 → 移動 → 地点 → 移動 …」の並びにする。地点は、観光の目的地（spot）と、公共交通機関の乗る駅と降りる駅（station）。駅やバス停は観光の場所ではないが、移動の目的地になるので、目的地と同じように1つの地点として扱う。移動は、歩く、タクシー、乗り物の1つずつに分ける。降りた駅でそのまま次の乗り物に乗るときは、乗り換えとして1つの地点にまとめる。駅の位置は乗り物の線の端から取り、地図に出している駅（/api/state の stops）と名前が合えば、場所の詳細を開けるようにする。結果の画面の一覧と一緒に出かける画面の場面は、どちらもこの並びを使う。

**結果の画面** 並びのとおりに、目的地、駅、移動を縦に並べる。目的地には到着〜出発の時刻と滞在時間、駅には着く時刻と出る時刻、乗る・降りる・乗り換える乗り物（番号の代わりに乗り物のアイコン）、移動には出発 → 到着の時刻とかかる時間と内訳（moveStepsHtml）を出す。

| 内訳 | 書くこと |
|---|---|
| 歩く | 距離、約何分 |
| タクシー | 距離、乗車と降車の時刻、乗っている時間、乗り場で待つ時間 |
| 公共交通機関 | 路線名、「〇〇駅 から乗って △△駅 で降りる」、乗車と降車の時刻、乗っている時間、待ち時間、距離 |

一緒に出かける画面の移動の場面にも、同じ内訳を出す。時刻のない古い保存データは、行き方の札だけを出す。

**一緒に出かける画面**（public/js/views/route.js の goOut）

| 場面 | 地図 | 文章 |
|---|---|---|
| 出発 | ルート全体。まだ行っていない場所と道は薄く | 日付、か所数、歩く距離と乗り物の距離、始まりの天の声 |
| n か所目 | その場所へ寄る | 時刻、場所名、天の声、場所の情報 |
| 移動 | その区間が入るように合わせ、今向かう区間を太く光らせ、推しが道や乗り物の線に沿って次の場所へ動く（map.js の moveAlong） | 出発と到着の時刻、所要時間、行き方の札、「〇〇と一緒に、△△に乗って□□へ向かう。」 |
| おつかれさま | ルート全体 | 締めくくりの天の声 |

場面は routeFlow の並びに、出発とおつかれさまを足したもの（出発 → 1か所目 → 移動 → 乗る駅 → 移動（乗り物） → 降りる駅 → 移動 → 2か所目 → …）。駅の場面では、着く時刻と出る時刻、乗る（降りる、乗り換える）乗り物を出し、地図の推しを駅に置く。移動の場面では、その移動1つ分の線を光らせ、推しをその線に沿って動かす。

上の進み具合には、地点の丸（どんな場所かのアイコン。目的地は右上に番号）と、その間の移動の小さな丸（移動手段のアイコン）を線でつないで横に並べる（多いときは横にスクロールし、今の場面を真ん中に出す）。どの丸を押しても、その場面へ移り、「次へ」で進んだときと同じ内容が出る。通った所は塗り、今の場面は白く大きくする。地図の乗り場の印も、まだ行っていないものは薄く、次に向かうものは目立たせる。下に「戻る」と、次の場面の名前の付いたボタン（「次は 西長堀駅 へ」「西長堀駅に到着」）を置く。スマホでは上に地図、下に文章、PCでは左に地図、右に文章。場所の情報のシートが上に開けるよう、重なり順はシートより下にする。

ミニ推しは喋らない。タイムラインと同じく、この機能の文章もすべて第三者視点の天の声で書き、吹き出しも使わない。「推し×推し」には、公式の関係ではないことを明記する。

## 17. ログインとプロフィール（lib/auth.js）

**ログインは必須ではない。** 目的は、別の環境で同じ利用者として使う場合に備えて、入力内容をクラウドに保存することだけである。クラウド保存は今回は実装しておらず、内容はこのアプリのサーバ内（`data/state.json`）に保存する。そのため現状では、同じサーバに接続できる環境どうしでのみ同じ内容を使える。

| 場面 | 動作 |
|---|---|
| 初めて開く | ログイン画面を出さず、すぐホームを開く。サーバが自動で利用者を作り、Cookieで同じ端末を覚える |
| ログインの入口 | プロフィール画面の一番下の控えめなボタンのみ |
| 登録 | 今の端末の内容にIDとパスワードを付ける。内容はそのまま引き継ぐ |
| ログイン | 登録済みの内容へ切り替える |
| ログアウト | この端末は新しい状態から始まる。登録した内容は再度ログインすれば戻る |

**個人情報を持たない。** プロフィールは呼び名（任意）、好きなもの、歩ける量の3項目で、サーバは決まった項目しか保存しない。呼び名が空なら文章では「あなた」と書く。ログインIDは半角英数字のみで、メールアドレスは受け付けない。

パスワードは Node.js 標準の scrypt でハッシュ化し、ユーザーごとのソルトと一緒に保存する。ログイン状態はランダムなトークンで判定し、サーバにはそのハッシュだけを保存する。Cookieは HttpOnly と SameSite=Strict を付ける。同じIDで失敗が続くと一時的に止める。

審査では、設定タブの「すべてのキャラとエリアを獲得する」を押すと、60日前に獲得した扱いになり、足あとが溜まった状態を見られる。

## 19. 追加分の制約

- 天気は創作で、実際の天気とは一致しない。
- ルートの文章は用意した文の組み合わせで、気分の言葉は辞書にある言葉しか読み取れない。読み取った内容は画面に示す。
- 大阪と尾道の間の線は実際の線路ではなく、つながりを示す直線。
- イベントの日程は2026年11月時点の公開情報で、未確定のものは仮の日付を置いている。
- 大阪の店舗の情報はグルメサイトなどの掲載情報で、公式サイトでは確認できていないため、リンクを置いていない。駅と一部の場所の座標は地図上の目安で、住所検索で求めたものではない。
- 京町ありさ以外のキャラの絵は、仮のSVG。`look.image` と `look.portrait` に画像を指定すると差し替わる。

## 20. AIを使用する箇所

**本アプリではAPIの接続ができないため、ダミーデータでAIを再現する。** 大会規定で外部のAPIに接続できないことが理由である。実際のサービスでは、次の7か所でAIをAPIで呼び出す。

| 番号 | ファイルと関数 | AIに任せること | 本アプリのダミー |
|---|---|---|---|
| 1 | `lib/simulator.js` の `chooseNext` | 推しの次の行き先を決める | 行動原理の数値による点数計算 |
| 2 | `lib/simulator.js` の `chooseDoing` | 訪問先での推しの様子を書く | 用意した文章から選ぶ |
| 3 | `lib/diary.js` の `writeDiary` | 1日の日記を書く | 訪問の記録を定型文に当てはめる |
| 4 | `lib/planner.js` の `readFreeText` | 気分の言葉の意味を読み取る | 登録した言葉との照合 |
| 5 | `lib/planner.js` の `planRoute` | 観光ルートと文章を考える | 点数計算と用意した文章 |
| 6 | `lib/spot-scorer.js` の `scoreSpot` | スポットと推しの相性を判断する（点数、理由、おすすめの一品） | 好みの言葉とスポットの特徴の照合と点数計算。バッチでまとめて呼ぶ |
| 7 | `lib/recommend.js` の `writeRecommendation` | 推しのおすすめの理由（スポットごとに別の理由）とおすすめを書く | そのスポットでの過ごし方の記録（時間帯、天気、滞在、していたこと）と、性格ごとの言い回しの組み合わせ |

### 切り替えの手順

API呼び出しのコードは、各箇所にコメントアウトで残している。ソースを「【AI差し替え箇所】」で検索すると見つかる。

1. `npm install @anthropic-ai/sdk` を実行し、環境変数 `ANTHROPIC_API_KEY` を設定する
2. `lib/ai.js` のコメントアウトを外す
3. 7か所のコメントアウトを外し、ダミーの処理と入れ替える
4. 呼び出し元の関数を async にして await を付ける

### 切り替えるときの注意

- 旅は毎回最初から計算し直している。番号1と2をそのまま置き換えると、画面を開くたびにAPIを大量に呼ぶので、1日分の結果を保存して使い回す形に変える必要がある。
- ミニ推しは喋らない。指示文で、第三者の天の声として書くよう伝えている。
- 呼び出すのはサーバ側だけで、ブラウザからは接続しない。

### ダミーであることによる違い

番号4は文章の意味を読み取らず、登録した言葉を含むときだけ反映する。読み取れなかったときは、そのことを天の声で伝える。

## 21. 推しのおすすめとスポットDB

推しのアイデンティティに合ったおすすめを出すため、エリアのスポット情報を集めてDBにし、推しごとの相性を点数にして行動とおすすめに使う。人気の順（口コミの上位）ではなく、推しの好みに合うかで決める。

### 流れ

| 段階 | ファイル | 内容 | 本アプリでの扱い |
|---|---|---|---|
| 収集 | `lib/spot-collector.js` の `collectSpots` | 場所ごとに基本情報、属性、営業時間、口コミと評価、予算、メニューを集める | 外部に接続できないため、`data/spot-sources.js` の「集めた結果」のダミーから作る。公式サイトの構造化データ（schema.org）などから集める処理を【API差し替え箇所】としてコメントアウトで残す |
| 相性 | `lib/spot-scorer.js` の `scoreSpot` | 推しの好み（likes、dislikes、interests、tastes）とスポットを照らし合わせ、0〜100の点数、理由（天の声）、おすすめの一品を出す | 【AI差し替え箇所 6/7】。ダミーは言葉の照合と点数計算。AIへの依頼文と出力の形をコメントアウトで残す |

### 相性の点数（ダミー）

基本12点に、場所の種類への関心（最大26点）、好きな言葉（tastes.keywords）と特徴の言葉やメニューの一致（3つまで、1つ10点）、公式設定の好きなもの（likes）に通じるもの（8点）、口コミの評価（3.5を境に1あたり8点）、予算（使えるお金の1.5倍を超えると12点の減点、以内なら4点の加点）を足し、苦手なもの（tastes.avoid、dislikes）があれば18点を引く。駅と宿は15点を引く。0〜100に収める。評価の影響は小さくして、人気だけで決まらないようにする。理由は、公式設定の好きなものに通じるとき、好きな言葉が合うとき、おすすめの一品、苦手なもの、予算の順に、天の声の文で書く（推しには喋らせない）。

例: こはる × 夕やけカフェ ドーナツは84点（公式設定の「できたてのドーナツ」に通じる。おすすめの一品はプレーンドーナツ）。こはる × 千光寺は1点（坂が苦手）。凪は大阪市立中央図書館、隆景は三原城跡、武蔵は道場が一番になる。

### 推しのおすすめの画面（public/js/views/recommend.js、#/recommend）

メニューの名前は「推しのおすすめ」（スマホのタブは2行）。上から次の順に置く。

| 部品 | 内容 |
|---|---|
| 推しの顔 | 押すと推しを切り替える |
| 好みの内訳（濃紺の面） | 推しの顔、「〇〇のおすすめ」、「一番のお気に入りは〇〇」（選んだエリアで相性が一番の場所）。エリアの札（すべてのエリア、三原市、尾道市、大阪市と件数。おすすめが2つ以上のエリアにあるときだけ）は、押すとそのエリアに絞り込む。エリアを変えると、帯と種類の札はそのエリアの中の内訳になり、種類の絞り込みはそのエリアにある種類だけに合わせ直す。立ち寄った回数を場所の種類ごとに色分けした1本の帯と、種類ごとの札（すべて、景色、食事、カフェ…と件数）。帯の色も札も、押すとその種類に絞り込む。もう一度押すと「すべて」に戻る |
| 地図 | おすすめの場所に、種類の色のハートに順位を入れた印と、場所の名前を置く（上位3つは大きい）。名前は、拡大率15以上ではすべて、引いているときは上位3つと選んだ場所だけに出す。印を押すと、その場所のカードへ移って光らせる。PCでは右に、スマホでは画面の上に固定する |
| カード | ジャンルの横にエリア（ピンのアイコンと市の名前）。種類の色の帯に大きな種類のアイコン、順位（1位は順位の札を黄色にし、PCでは2列の幅で見せる。帯の高さは他と同じ）、相性（赤いハートに点数）。ジャンル、名前、立ち寄った回数と時間の棒（いちばん多い場所を100%）、理由（天の声の2文）、おすすめ（一品か時間帯）、営業時間・予算・評価の札。「くわしく見る」で外観、住所、メニュー（おすすめの一品にハート）、口コミ |

地図とカードはつながっている。地図のハートを押すとそのカードへ移り、カードのリンクやボタン以外のところを押すと、地図がその場所を真ん中にして動き、ハートを光らせて名前を出す。スマホでは地図を画面の上に固定し、カードだけが下でスクロールする。地図のすぐ下に来たカードの場所を地図が追いかけるので、地図を見るためにページを戻らなくてよい。ハートを押したときは、カードが固定した地図のすぐ下に来るように移る。

並び順は、好みの内訳の面の下の「並び順」で、「お気に入り順」（相性の高い順。同じ点なら立ち寄った回数の多い順。最初はこちら）と「訪れた回数順」（同じ回数なら相性の高い順）を切り替える。カードの順位と地図のハートの番号も、選んだ並び順に合わせる。「一番のお気に入りは〇〇」は、並び順にかかわらず相性で決める。候補は、立ち寄った回数の多い場所から最大40件。

種類の色は、食事は黄、カフェはミント、甘味・パンは桃、店は空色、景色は緑、寺社は橙、歴史・美術は砂色、図書館は藤色、道場は珊瑚色。色だけに頼らず、アイコンと名前も必ず添える。最大40件を返し、画面で種類ごとに絞り込む。

### おすすめの理由（lib/recommend.js、【AI差し替え箇所 7/7】）

ほとんどのスポットが同じ理由にならないよう、そのスポットでの推しの過ごし方の記録（足あと）から、スポットごとに別の理由を書く。

| 材料 | 例 |
|---|---|
| よく来る時間帯（朝、昼、午後、夕方、夜） | 「夕方、空の色が変わりはじめるころに中之島公園へ立ち寄ることが多い。」 |
| 雨の日、休みの日、平日 | 「雨の日になると、凪の足はなぜか庵 小径へ向く。」 |
| 平均の滞在、回数、通いはじめた時期 | 「おのみち歴史博物館に入ると、あかねは1時間51分ほど出てこない。」 |
| 前に来たときの様子（足あとの描写） | 「前に工房尾道帆布へ来たときは、棚を端から順にのぞいて、何も買わずに満足そうに店を出た。」 |
| 好みとのつながり（性格ごとの言い回し。相性で合った好みの言葉を入れる） | 「撮りためた写真を見返すと、中之島公園の景色が何枚も出てくる。」（ありさ）「甘味の話になると、こはるは急に早口になる。」 |

1文目は過ごし方、2文目は好みとのつながりか前に来たときの様子。どちらも場所の名前やジャンルを入れ、同じ推しのおすすめの中では、同じ理由の文を二度使わず、同じ言い回しは2回までにする。おすすめは、メニューのある店なら相性で選んだ一品、ない場所ならよく来る時間帯（「朝（9時ごろ）に行く」）。「〇〇なら、きっと〜を選ぶ」という文は書かない。

### スポットを約10倍に増やした（デモ用の架空のスポット）

実在の53か所に、デモ用の架空のスポット501か所（尾道246、三原51、大阪204）を足して554か所にした。`tools/build-spots.js`（`npm run build-spots`）が作り、`data/extra-places.json` に書き出す。`data/world.js` がそれを PLACES に足し、管理画面で保存した内容（data/content.json）にも、なければ足す（`lib/content.js`）。

- 実在の店の名前や住所を作らないよう、名前は「麺処 汐見」「古本屋 しおさい」「猫小路 朝凪」のような架空の組み合わせにし、説明に「デモ用に作った架空の場所です。実在しません。」、住所に「（架空の場所のため番地はありません）」と書く。fictional と generated の印を持ち、推しのおすすめや観光ルートでは「架空の施設」の印を出す。エリアの「主な場所」には実在の場所だけを並べ、架空のスポットは数を書く
- ジャンル（trait）は、ラーメン、うどん、お好み焼き、カレー、定食、喫茶、カフェ、自家焙煎の珈琲店、和菓子、パン屋、ジェラート、洋菓子、本屋、古書店、雑貨店、文具店、器の店と工房、猫の集まる路地、山、海辺、展望の場所、川辺、公園、寺、神社、古い町並み、資料館、道場（武蔵だけ）。外観、メニュー、予算、口コミは `data/spot-sources.js` のジャンルの雛形（ダミー）。山や海辺、川辺、路地などの自然や屋外は24時間
- 位置は、国土地理院の道路データ（`tools/build-routes.js` と同じで、保存したタイルを使うので通信しない）の交差点から、他の場所と35m以上離れたところを選ぶ。乱数の種が固定なので、何度作っても同じになる
- 経路は全組み合わせではなく、近くの6か所とエリアの駅、いちばん近い実在の場所との間だけを計算して `data/routes.json` に足した（2681件。ファイルは約2.3MB）。保存のない組み合わせは、`lib/simulator.js` の routeBetween が、保存した経路のつながりの上で所要時間が最短の道を探し（出発地ごとに覚えておく）、途中の場所を経由する経路をつないで作る。続けて歩く区間は1本にまとめる

### 行動への効き方の調整

スポットが増えると、種類への関心（interests）だけでは推しのアイデンティティが出にくい（本好きの凪でも、店（shop）への関心が低いので本屋に寄らない）。そこで次のようにした。

| 箇所 | 内容 |
|---|---|
| 相性の点数（`lib/spot-scorer.js`） | 好きな言葉が2つ以上合う場所は、場所の種類への関心が低くても、関心0.8とみなして点を付ける |
| 立ち寄り先の選び方（`lib/simulator.js` の tasteInterest） | 相性が60点を超える場所は、相性から見た関心（100点で1）と種類への関心の高いほうを使う。そのうえで affinityBonus（50点を境に最大2.2点）を足す |
| 観光ルート（`lib/planner.js`） | 同じジャンルを選んだ数の2乗に3点をかけて減点し、同じジャンルばかりのルートにしない。渡船やロープウェイを含む区間でタクシーを使うときは、電車やバスの部分もタクシーにして1台にまとめる |

過去の行動記録（足あと）は、創作の一か月の履歴（data/demo-history.js）からその都度計算しているので、スポットと相性が変わると作り直される。例えば、凪は図書館のほかに古書店へ、こはるはドーナツ店のほかにラーメン店やパン屋へ、ルイは猫の集まる路地へ、隆景は古い町並みや海辺へ、武蔵は道場のほかに山へ通うようになる。

### 本物に切り替えるとき

1. `lib/spot-collector.js` の collectFromWeb のコメントアウトを外し、collectSpots の中で使う（サイトの利用規約と robots.txt を守り、間隔をあけて集める）
2. `lib/spot-scorer.js` の AI の呼び出しのコメントアウトを外し、scoreSpot と入れ替える（lib/ai.js の手順）
3. 収集とAIが非同期になるので、`lib/spot-db.js` の runBatch を async にして await を付ける
4. 画面の「ダミーデータです」の注意書きを、出どころの表示に変える

### 直した不具合

| 不具合 | 原因 | 直し方 |
|---|---|---|
| 推しを全員獲得すると、ボタンを押しても反応が遅く、動かないように見える | ホームが30秒ごとに7人分の足あとを読み直し、そのたびに一か月分の行動を最初から計算し直していた（1人0.1〜0.5秒、起動直後は2秒以上）。その間はサーバが他の操作に答えられない | その日の訪問の計算は、日付の中では何時に計算しても同じなので、日ごとに覚えて使い回す（lib/simulator.js の DAY_CACHE。鍵は推し、内容の版、獲得日時、連れて行った履歴）。他の人の推しの足取りも日ごとに覚え、起動時に先に計算しておく。1分ごとの読み直しは1人20ms前後になった |
| 推しのおすすめで推しを続けて切り替えると、前の推しの結果が後から表示されることがある | 先に頼んだ結果が遅れて届き、上書きしていた | 最後に頼んだ結果だけを使う。別の画面へ移った後に届いた結果は捨てる |
| 学校のある日に、放課後に新幹線で遠くのエリアへ向かい、夜遅くに帰ってくる | 連れて行ったエリアが遠くても、寝る時刻までに帰れるかを見ずに出かけていた | 遠くのエリアへは、着いて60分過ごして寝る時刻までに家へ帰れるときだけ出かける。行けないときや、寝る時刻までに着ける場所が残っていないときは、今いる場所で時間をつぶさずにそのまま家へ帰る |
| 1日をなぞるつまみで、6時より前の出来事（朝5時に起きる武蔵など）を選べない | 帯が6時から始まっていた | その日の最初の出来事が6時より前なら、帯をその時まで広げる（3時まで）。目盛りは帯の上の本当の位置に置き、端の時刻の札が切れないようにする |
| 出会うのコードを空のまま押すと、前の結果の文が残る | 空のときは何もしていなかった | 「コードを入力してください」と出す |
| 推しのおすすめで、好みの内訳の帯や種類の札、並び順を押しても切り替わらない（2026年11月5日の報告） | 並び順のボタンの印に data-order を使っていたが、設定のタイムラインの順番が <html> にも data-order として付いている。押した場所から外側へボタンを探すと、どこを押しても <html> が「並び順のボタン」と見なされ、絞り込みの前に処理を終えていた。並び順のボタンも、どちらも選ばれていない見た目になっていた | 並び順のボタンの印を data-sort に変え、押されたボタンは好みの内訳の面の中だけで探す。画面のボタンの印に <html> の属性と同じ名前を使っていないかを、テストで確かめる |
| 一緒に出かける画面を、推しが動いている途中や地図が動いている途中に閉じると、エラーが出る | 片付けた地図の推しの印を、後から動かそうとしていた | 動かす前に印が残っているかを確かめる。地図を片付ける前に動きを止める（ホーム、観光ルート、推しのおすすめも同じ） |

| 足取りの上の乗り場 | ホームの地図で、公共交通機関を使った区間の、乗った駅と降りた駅（バス停、桟橋、ロープウェイの駅）に乗り物のアイコンを出す。乗り換えで重なるときは1つにまとめ、なぞった時刻より後のものは薄くする |
| 初期のエリア | ありさの地元（大阪市）と武蔵の地元（尾道市。尾道の長屋に仮住まいしている設定）。そのため新しい利用者では、AREA-ONOMICHI と MINI-MUSASHI は「もう獲得しています」になる |
| 推しの家 | 本文の「架空の自宅2か所」に対して、7人それぞれに架空の家を置いた（行き先の候補にはならない） |
| 実在の場所 | 駅や乗り場を含めて64か所。これにデモ用の架空のスポット5010か所と、武蔵だけが訪れる架空の道場とジム8か所を足して、合計5089か所 |
| 経路の保存 | 全組み合わせを保存すると数百MBになるため、国土地理院の道路データから作った道のグラフ（約1.4MB）を data/routes.json に保存し、lib/router.js が実行時にダイクストラ法で最短の道を求めて控えておく。地下鉄は線路の線をたどり、たどれない区間は直線で描く |
| 武蔵の夜 | 宿を探さず、移された駅で夜を明かす（camp） |
| 観光ルートの見出し | 「○○が考えるルート」という名前は使わず、日付とエリアを見出しにする |
| 管理画面のログイン | README に書いたデモ用の値（ID admin、パスワード mini-oshi-admin）。環境変数で変えられる |
| 天気の地方 | 大阪市は関西、尾道市と三原市は瀬戸内として、同じ地方は同じ天気になる |
| 画面の最小幅 | 横幅320pxを最小とする（それより狭いときは横にスクロール）。320〜374pxでは文字とボタンを少し小さくして、はみ出さないようにする |
