# ミニ推し！ 要件定義（依頼者の指示書）

> 2026-11-09 に依頼者から受け取った指示書の全文。食い違いの扱いと依頼者に確認した事項は [設計書.md](設計書.md) の末尾「0. 開発時の確認事項」にまとめる。

あなたはこの指示書だけを読んで、以下のアプリを開発してください。過去の経緯を知っている必要はありません。指示が食い違って見えるときは、「8. 採用しないもの」を優先してください。

第1章から第8章は依頼者が指定した要件です。第9章は依頼者の指定が解釈を要する箇所、第10章は依頼者の指定ではない現行実装の参考情報です。

## 1. 目的と前提

- 約10時間でWEBサービスを開発するコンテストの競技用アプリを作る。
- ローカルサーバを建て、localhost内で動くWEBアプリとする。
- 既存のスタンプラリーWEBアプリ（https://app.raund.net/nttw-demo/ ）に付随して使うことを想定する。
- アプリの題は「ミニ推し」。ロゴの表記は「ミニ推し！」。

## 2. コンセプト（決して忘れないこと）

- ミニ推しとは、獲得したキャラが実際の場所を旅する様子を見ることができるWEBアプリである。
- キャラの旅は、そのキャラの行動原理を元にAIが判断する。
- **キャラクターの行動を楽しむこと**がコンセプトである。すべての判断でこれを優先する。
- 推し活をする人は「推し＞自分」であり、推しが行く場所や食べるものを自分も味わってみたいという気持ちで成り立っている。
- たくさんのキャラクターを集めていくアプリではあるが、あくまでも**「自分の推し」を楽しむアプリ**である。作品と推しを尊重する作りにする。
- アプリの目的は、**スタンプラリーのユーザーを再訪させること**である。

## 3. 大会規定（厳守）

- PHPの利用は禁止。
- 外部のAPIに接続することは禁止。
- 例外として、地図を使う場合は国土地理院の無料WEBサービスにアクセスしてよい。

## 4. 成果物

次の3点を提出できる状態にする。

1. アプリケーション
2. ソースコード。他者が後から見返せるようにコメントを付ける
3. 設計書

## 5. デザイン

- モバイルファーストで作る。
- 若者が使いたいと思うようなデザインにする。
- アップルのような、シンプルでモダンで革新的なデザインと、UIにする。UIには革新性が求められている。
- ゲームのように柔軟にレイアウトを考え、最も使いやすく最も素敵なデザインにする。
- 全体的に文字を減らし、アイコンなどで直感的に操作できるようにする。
- スマホとPCの両方に対応する。レスポンシブで画面が変わり、PCで使うときはPCに最適化された画面にする。
- 配色は `#ffdd00`、`#b5decc`、`#007190` を使う。

## 6. 画面

ロゴ「ミニ推し！」を一番上に表示する。

大メニューのタブは次の6つで、この順番とする。

1. ホーム
2. 出会う
3. ミニ推し
4. 観光ルート（保存した観光ルートの一覧）
5. エリア
6. 設定

### ① ホーム

一人の推しを楽しむ画面にする。

- キャラクターのアイコンを一列に並べて選ぶ形にはしない。
- ホームに出すミニ推しは、獲得した全員ではなく、ミニ推しの一覧で選んだものだけにする。「自分の推し」と楽しむアプリなので、不特定多数のキャラを並べない。
- 選んだミニ推しの中での切り替えは簡単にし、何ができるのかが見て直感的に分かるUIにする。一つの世界観に没入できるUIにする。
- メインはミニ推しが旅をしているのを見ること。推しの絵を大きくしすぎず、スクロールしなくても推しの今と足あとの情報が見えるようにする。
- 「ルートを考えてもらう」は使ってほしい機能だが、メインではない位置づけで置く。
- イベント情報はトップページで目立たせない。

次の内容を置く。

1. 推しの世界（作品と推し）
2. 選んだキャラの現在地と行動履歴。マップ上に表示する
3. 歩数と距離。キャラの特性を踏まえた値にする
4. タイムライン

**タイムライン**

- 地図よりタイムラインをメインにする。
- 最初は今日の分を表示する。カレンダーで日付を選ぶと、過去の行動も見られる。
- 文章で表示する。
- 何時何分にどこを訪れたかという文章にする。
- 第三者目線の表示にする。キャラに喋らせない。
- 訪れた理由の文章は入れない。

**歩数と距離**

- 今日は歩数と距離だけを表示する。どのように歩いたかなどの文章は入れない。
- 別の日を選んだときは、iPhoneのフィットネスのように歩数や距離をグラフィカルに表示する。色はアプリの色合いに合わせる。
- 別の日を選んだときは、1日の行動の簡単なまとめを日記のように読めるようにする。ミニ推しは喋らないので、天の声が第三者の視点で書く。
- 歩数を競わせているようなデザインにしない。

**場所の情報**

- ホームの中で場所に関する部分（例: カフェ）をタップすると、その場所の情報（URLなど）を表示する。

**エリアと行動**

- ミニ推しは常に旅に出ているわけではない。エリアに設定した時点から行動を始める。
- 選べるエリアは1つだけ（複数選択はできない）。
- エリアを変更するボタンの周りに、エリアの一覧は置かない。
- エリアを切り替えたら、即時に移動する。
- 移動したことをタイムラインに「神の手が〇〇を□□エリアに移動させた」のような文言で反映する。
- 移動の間はポップアップでアニメーションを出し、文言は「エリア切り替え中」とする。移動が終わったら閉じる。
- 家に連れて帰るときは、タイムラインに「神の手が〇〇を家に帰した」と表示して旅を終える。エリアが指定されていないときと同じ状態に戻す。
- 地元のエリア以外へ移動したときは、キャラクターの性格に応じて「知らない場所に来た」という行動をさせる。臆病な性格なら都会の駅で途方に暮れ、アクティブな性格なら初めての場所にわくわくして憧れの雑貨屋に入るなど、性格の特性が出る行動にする。
- エリアを選ぶときに、推しを物のように「置く」と表現しない。推しを人として扱う言葉にする。選択画面の見出しは「〇〇をどこに連れ出す？」とする。

**舞台のボタンの名前**

- ルート作成のボタンは「観光ルートを考えてもらう」とする。
- イベントのボタンは、推しが今いるエリアのイベントだと分かる名前にする。

**ミニ推しの一覧**

- ホームに連れて行く操作は、文字ではなくアイコンで示す。

### ② 出会う

- QRコード読み取りとコード入力のどちらかを選べる。
- そこからキャラやエリアを獲得できる。
- これらは現地に行かないともらえないものとする。

### ③ ミニ推し

- 獲得したキャラのコレクションを見ることができる。
- 作品ごとに分ける（例: 漫画作品、映画作品、企業キャラクターなどの分類）。作品や推しを尊重する作りにする。
- 旅先で出会った他の人の推しの一覧を、時系列順で並べる。いつどこで出会ったかを表示する。
- 出会った他の人の推しは閲覧のみとし、自分の推しとして使うことはできない。

### ④ エリア

- 獲得したエリアのコレクションを見ることができる。
- マップではなく、獲得エリアの一覧を並べて表示する。
- タップすると、エリアの情報と過去の旅の履歴が見られる。
- カレンダー機能で、その地域のイベント情報を見られるようにする（第7章「地域のイベント」）。

### ⑤ 設定

- 内容は開発者に任せる。
- 「解釈違いを報告する」から、推しのキャラクター性（性格、行動、文章など）についての意見を送れる。推し、どんな解釈違いか（性格・人柄、行動・行き先、日記やタイムラインの文章、観光ルート、見た目、その他）、どこで見たか（任意）、内容（5〜1000文字）を送る。
- ミニ推しのキャラクター性は公式が判断するものなので、意見が必ずしも反映されるわけではないこと、個別の返事はしないことを、送る前と送った後に注意書きで伝える。個人を特定できることは書かないよう案内する。
- 報告は外部のサービスには送らず、アプリのサーバに保存し、管理画面の「解釈違いの報告」で読む（未読、確認済み、公式に共有の状態を付けられる）。

### 全画面共通

- キャラやエリアの獲得数の母数は表示しない。

## 7. 機能

### キャラクター

- スタンプラリーのWEBアプリ（https://app.raund.net/nttw-demo/ ）のキャラクターを初期キャラとして使えるようにする。名前は「京町ありさ」とする。
- 実在の戦国武将も推しキャラとして出てくるようにする。

### 移動

- キャラはマップの道の上を歩く。
- 可能であれば、歩くだけでなく、電車などの公共交通機関にも乗る。

### 場所

- デモであっても、実際の場所に対応させる。

### マップのエリア

- 獲得したエリアの外と区別するため、マップ上のエリアを区切って表示する。
- 区切りの単位は小さなエリアに分けず、大きく一つ（市区町村レベル）とする。

### 他の人の推しとの出会い

- 他の人の推しと出会えるようにする。例: 北海道で獲得したキャラを、この場所で旅させている人がいる場合。
- そのキャラの獲得した場所や、その地域の紹介などを互いに見られるようにする。
- 目的は、興味を持ってもらい、その地域へ旅したいと思ってもらうこと。

### デモ

- サンプルのコードを用意し、入力するとホーム画面などに反映されるようにする。

### 推しのキャラクター性と行動原理

- 一般に「公式」と呼ばれる原作、アニメ作品、ゲーム作品などの情報から、キャラクター性を深掘りする。
- 架空アニメのキャラ「京町ありさ」について、性格、住んでいる場所、通っている学校、よく通る店、作中での行動などを細かく創作し、キャラの行動原理に組み込む。
- 旅行だけでなく「日常」を反映する。例: 平日の日中は常に学校にいる、家に帰るまでに寄り道する、雨の日はまっすぐ帰る。
- 作中のN西市は大阪府京町周辺とする。そのあたりの実在の高校や建物を作品のモデルになった場所とし、実際に住んでいるところから通っている学校へのルートなども創作する。

### 宮本武蔵と小早川隆景

- 小早川隆景のアイコンは、小早川隆景の肖像画にする。
- 村上武吉は削除し、代わりに宮本武蔵を入れる。アイコンは肖像画にする。
- 宮本武蔵は、道場破りをして決闘を求めるキャラクターとする。他のキャラと行動を差別化するため、ボクシングジムや空手道場をめぐるなど極端な行動を取らせる。
- 旅先で出会う真田信繁のアイコンも、肖像画にする。
- 京町ありさと宮本武蔵は、すでに一か月くらい色々なエリアを旅しているようにデータを創作する。

### 地域のイベント

- カレンダー機能を追加し、その地域のイベント情報を見られるようにする。
- イベント情報は推しの行動にも反映する。キャラクターの性格によって興味を持ったり、駅のポスターを眺めたりする。
- カップリングルート作成の画面で期間を選ぶと、その期間のイベントもルートの検討に反映する。

### AIの扱い

- 実際にはAIをAPIで呼び出して使用するところは、API呼び出しのコードをコメントアウトで残し、その部分だけ入れ替えればよいことが分かるようにする。
- 仕様書にAPIでAIを使用するところを記載する。
- 本アプリではAPIの接続ができないため、ダミーデータでAIを再現する。

### 天気、使い方、保存したルート

- 天気を行動に反映する。天気は外部のAPIを使わず、創作で付ける。時間ごとの天気を出す。
- 初めて利用する人のために使い方の説明を置く。項目は、推しの行動を観察できるアプリであること、エリアに連れ出すと行動を始めること、たくさん行動した推しが観光ルートを考えてくれること、推しと推しの組み合わせをシミュレーションできること、イベントなどで推しを追加できることとその方法、ログインで他の端末でも利用できること。
- 推しに作ってもらった観光ルートを保存し、一覧と詳細を見られるページを作る。

### カップリングルート作成

ユーザーが能動的に推しの世界に参加できる機能として、「推し×自分」「推し×推し」のカップリングルート作成機能を追加する。推しが自分のために観光ルートを選んでくれる機能であり、推しと別の推しを組み合わせたらどうなるかをシミュレーションできる機能でもある。イメージは「推しが考えたルートを推しと一緒に観光することができる夢みたいな機能」。

- 「自分」についてはプロフィールを登録できるようにする。
- そのプロフィールを元に、推しが観光ルートを作成する。
- ルート作成中は、推しが考えているようなアニメーションが入ったローディング画面を出す。
- 「推し×自分」か「推し×推し」を選べる。もうひとりの推しはその都度選択する。
- 気分は「推し×自分」のときだけ入力できる。選択肢に加えて、言葉でも入力できる。「推し×推し」では選べない。
- 目的は入力させない。推しが自分のために考えたルートであることが大切で、その方がキャラの個性を出しやすいため。
- **ミニ推しは喋らない。** 推しの台詞や吹き出しは使わず、文章はすべて天の声（第三者視点）で書く。
- 推しのタイムラインが蓄積されているほど、よく立ち寄った場所や長く滞在した場所が蓄積されているので、そのデータも参照する。

### ログインと個人情報

- ログインの目的は、別の環境で同じユーザーが使う場合を想定して、入力内容をクラウドに保存することだけとする。今回クラウド保存は実装しなくてよい。
- ログイン機能は前面に出さない。プロフィール画面にログインボタンが置いてある程度の控えめな位置にする。
- 個人情報が特定されるような情報は、基本的に入力させない。

### 推しのおすすめとスポットDB（2026年11月5日の追加）

- 推しのアイデンティティ（好みや行動原理）に合ったおすすめを出す。ラーメンが好きな推しはラーメン店、山が好きな推しは山、本屋が好きな推しは本屋を、口コミの上位ではなく、推しの個性が出る形ですすめる。
- エリアの店舗や施設の情報をWebから集めてデータにする。集める項目は、スポット名、住所、外観などの基本情報、スポットの属性（何の店か）、営業時間（自然物は24時間）、口コミと評価、店なら予算とメニュー。
- 集めたデータはバッチで定期的に更新する（1日1回。手でも動かせる）。
- 集めたデータと推しのアイデンティティを組み合わせてAIで分析し、推しごとにスポットとの相性を点数にして、理由と一緒にデータベースに保存する。
- 相性の点数をもとに、推しがどのスポットに立ち寄るかの行動原理を調整する（観光ルートの場所選びにも使う）。
- 多く立ち寄ったスポットを、その推しのおすすめとして利用者にすすめる。メニューに「推しのおすすめ」のアイコンを足し、推しごとに一覧で見られるようにする。
- スポットのデータを約10倍に増やす（実在の53か所に、デモ用の架空のスポット501か所を足して554か所）。ラーメン、うどん、お好み焼き、喫茶、自家焙煎の珈琲店、和菓子、ジェラート、本屋、古書店、雑貨、器の店、猫の集まる路地、山、海辺、川辺、寺、神社、古い町並み、資料館、道場など、推しのアイデンティティに合うジャンルをそろえる。架空のスポットは実在しないことを説明と画面の印で示し、エリアの「主な場所」には実在の場所だけを並べて架空のスポットは数を書く。
- 増やしたスポットに合わせて、過去の行動記録（足あと）も作り直す。相性の高い場所は、場所の種類への関心が低くても立ち寄るようにし（本好きの凪は古書店へ、こはるはラーメン店やパン屋へ、ルイは猫の路地へ、武蔵は山と道場へ）、観光ルートは同じジャンルばかりにならないようにする。
- 大会規定で外部のAPIやWebサイトに接続できないため、Webからの収集とAIの分析はダミーデータで再現する。その部分のプログラムだけを差し替えれば本物になるようにし、差し替えのコードをコメントアウトで残す。スポットの外観、メニュー、予算、口コミがダミーであることは、画面に必ず書く。

### 推しのおすすめ（2026年11月5日の変更）

- 「お気に入り」の名前を「推しのおすすめ」に変える。
- 「〇〇なら、きっと〜を選ぶ」という文はなくし、「〇〇が選びそうな一品」は「おすすめ」にする。
- おすすめの理由は、スポットごとに別のものを創作する（そのスポットでの過ごし方の記録をもとにする）。
- 相性は、円ではなくハートと数字のアイコンで見せる。「相性は、〇〇の性格と好きなものから見たもので、人気の順ではない。」の文は消す。
- 並びは相性の高い順にする。あとから、「お気に入り順」（相性の高い順）と「訪れた回数順」を切り替えられるようにした。「一番通うのは〇〇」は「一番のお気に入りは〇〇」、「〇〇のおすすめ n か所」は「〇〇のおすすめ」にする。
- カードのリンク以外のところを押すと、地図がそのスポットを真ん中にして動く。地図のハートには場所の名前を出し、どのスポットかわかるようにする。スマホでは地図を見たままカードを読めるようにする（地図を上に固定し、読んでいるカードの場所を地図が追いかける）。1位のカードの帯の高さは、他のカードと同じにする。
- カードに、そのスポットがどのエリアにあるかを書き、エリアでも絞り込めるようにする（種類の絞り込みと組み合わせられる）。
- 場所の種類（カテゴリー）で絞り込めるようにする。縦に並べるだけでなく、好みの内訳の帯、地図のハートの印、種類の色のカードで、グラフィカルに見せる。

### 運営の管理画面

- 運営側の管理画面を作成する。ユーザーからは見えない、完全に独立した存在とする。
- 必要な要素は開発者が考えて追加する。

## 8. 採用しないもの

次のものは、過去に試して依頼者が取りやめた。作らないこと。

- キャラ「村上武吉」。宮本武蔵に入れ替えた。
- キャラ名「福本ひより」。「京町ありさ」に変更した。
- ボタン名「○○が考えるルート」。
- インスタグラム風のデザイン。すべて忘れること。
- 「今日を再生」機能。
- タイムラインを写真つきの投稿にする見せ方。
